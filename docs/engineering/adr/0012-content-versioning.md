# ADR 0012 — Content Versioning and Validation

**Status:** Proposed

## Context

Non-negotiable rule 10: "Content is data, rules are code. Definitions, localized text, portraits, names, traits, buildings, goods, events, and region profiles are authored data. Core invariant enforcement stays in tested code." `tech-stack.md` states the pipeline this feeds: "Authored JSON and CSV are inputs to the .NET content compiler. JSON Schema, stable string IDs, uniqueness, and references are validated before normalized runtime JSON is emitted." Roadmap Phase 3, items 4–6 require replacing "the catch-all content schema with typed definition families: goods, buildings, traits, policies, events, regions, cultures, religions, names, and presentation metadata," adding "cross-file reference validation, duplicate-ID detection, enum/range validation, inheritance/patch rules, localization-key checks, and deterministic normalized output," and "a content manifest with schema version, compiler version, source hashes, and dependency order." Phase 3's exit gate: "Invalid references and schema violations fail before Unity starts." The current-state audit is explicit about how far the skeleton is from this: "The authored content catalog contains only `status.placeholder`. The JSON Schema requires only an `id` and permits every other property."

The design corpus supplies a live, concrete cautionary case that makes this ADR's stakes tangible rather than abstract: the design-authority registry's cluster 10 documents that `gens-resources-goods-design.md` is "self-declared 'the complete, authoritative registry'" for every good, explicitly superseding `gens-buildings-design.md` §2's goods taxonomy and `gens-estate-settlement-design.md` §8's simplified storage list — but both superseded lists are "flagged by the source doc itself as unfinished work," still present, uncleaned, in their original documents. The registry's own words: "Both still contain their own now-superseded partial lists; this pass makes that gap larger, not smaller, and it's the most concrete remaining task before implementation." If the content compiler simply ingested whichever goods list a JSON author happened to copy from, it would silently reproduce this exact contradiction at runtime — the precise failure mode Phase 3's "duplicate-ID detection" and "cross-file reference validation" exist to catch mechanically rather than relying on a design document's own self-audit.

Rule 13 also bears directly here: "AI is additive, asynchronous, and replaceable... it cannot decide authoritative outcomes, invent resources... or make a save dependent on a provider" — content authored or assisted by an AI provider (per `tech-stack.md`'s `IArtGenerationProvider` and roadmap Phase 18's "generated-art providers") is not a separate content path; it produces the same JSON/CSV shape and goes through the identical validation this ADR defines.

## Decision

- **One goods list, one source of truth per `DefinitionId<T>` namespace.** Every content family (goods, buildings, traits, policies, events, regions, cultures, religions, names, presentation metadata — the exact list Phase 3, item 4 names) has exactly one authoring location in the content tree; the compiler rejects a duplicate `DefinitionId` (ADR 0001) across files in the same family as a hard build failure, not a warning — this is the concrete, automatable fix for the Buildings/Estate & Settlement goods-list contradiction the registry flags as still-live prose-only duplication.
- **A content pack manifest** records `SchemaVersion` (the typed-definition-family schema shape, bumped on a breaking schema change, distinct from `SaveFormat.CurrentVersion`), `CompilerVersion`, a SHA-256 `SourceHash` per input file, and a `DependencyOrder` (which content families reference which others — e.g., a Building recipe referencing Good `DefinitionId`s — computed and stored, not re-derived at runtime).
- **Definitions are additive within a schema-version's minor revision**: new fields with defaults, new definitions, and new enum values may be added without bumping `SchemaVersion`. A breaking change (removing a field, changing a `DefinitionId`'s meaning, narrowing a range) bumps `SchemaVersion` and requires a content migration function, mirroring ADR 0011's save-migration shape exactly but operating on content JSON rather than save JSON.
- **Retirement, never deletion.** A superseded definition (the exact situation `gens-buildings-design.md` §2's goods list is in today, per the registry) is marked `status: "superseded"` with a pointer to its replacement `DefinitionId`, rather than deleted — deleting it would silently break any already-saved campaign or historical content referencing it; the compiler still validates it (so a tombstoned definition can't itself reference something invalid) but flags any *new* content authoring against it as an error.
- **Cross-file reference validation, duplicate-ID detection, enum/range validation, and localization-key checks all run in CI**, gating every content-pack build exactly as Phase 3's exit gate requires ("Invalid references and schema violations fail before Unity starts") — before any Unity or headless-runner step consumes the pack.

## Consequences

- The Buildings-doc/Estate & Settlement goods-list contradiction the design-authority registry flags becomes mechanically unrepresentable once the content tree is built this way: whichever list is authored second trips duplicate-`DefinitionId` validation immediately, forcing the "back-porting" cleanup the registry calls "the most concrete remaining task before implementation" to actually happen as part of getting content to compile, rather than remaining a documented-but-unenforced risk.
- AI-assisted content authoring (rule 13) needs no special validation path — it is subject to identical schema, reference, and duplicate-ID checks as hand-authored content, which is the concrete mechanism behind rule 13's "cannot decide authoritative outcomes" for content specifically.
- A save's recorded content-pack hash (ADR 0010) plus this ADR's manifest lets a load path detect "this save was authored against different content than is currently installed" before a dangling `DefinitionId` reference causes a confusing runtime failure deep in gameplay code.

## Alternatives Considered

- **Schema-version content strictly frozen once shipped, no additive-within-minor-version allowance.** Rejected: would force a full content migration for every new trait or good added during ordinary content-authoring work (Phase 5's "small representative slice" of the trait catalog explicitly anticipates growing later), which is disproportionate — additive changes are exactly the low-risk case migrations exist to avoid needing.
- **Allow multiple authoritative lists per content family, resolved by a runtime precedence rule (last-loaded wins, or an explicit override file).** Rejected: this is precisely the shape of the Buildings/Estate & Settlement contradiction already causing confusion in prose; a runtime precedence rule would encode the ambiguity into the engine instead of removing it.
- **Soft warnings instead of hard build failures for duplicate IDs and reference violations.** Rejected by Phase 3's own exit-gate wording ("fail before Unity starts") — a warning that doesn't block a merge or a build is, in practice, ignored, which is exactly the current state the roadmap's audit describes ("The JSON Schema requires only an `id` and permits every other property").
